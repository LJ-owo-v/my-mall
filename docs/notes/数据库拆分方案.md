## 一、现状盘点

### 1.1 表分布：**76 张表 / 5 个前缀 / 单库 `mall`**

| 前缀 | 表数 | 语义 | 当前归属服务 |
|---|---|---|---|
| **`ums_`** | **25** | 用户 / 会员 / 权限 / 角色 | `my-mall-user` |
| **`pms_`** | **18** | 商品 / SKU / 分类 / 品牌 | `my-mall-product` |
| **`sms_`** | **13** | 营销 / 优惠券 / 秒杀 | `my-mall-marketing` |
| **`cms_`** | **12** | 内容管理（话题/专题/帮助） | `my-mall-product`（当前） |
| **`oms_`** | **8** | 订单 / 购物车 / 退货 | `my-mall-order` |

### 1.2 服务清单（9 个）

| 服务 | 端口 | 是否有表 |
|---|---|---|
| `my-mall-user` | 8086 | ✅ `ums_*` |

| `my-mall-order` | 8089 | ✅ `oms_*` |
| `my-mall-file` | 8090 | ❌（OSS） |

| `my-mall-auth` | 8401 | ❌（鉴权） |

## 二、核心难点：跨域访问

### 2.1 实测的跨域访问矩阵

通过对各服务 XML 中表名的静态扫描得出：

| 服务 | 访问的表前缀 | 跨域判定 |
|---|---|---|
| `my-mall-user` | `ums` (10) | ✅ **纯粹** |
| `my-mall-order` | `oms` (7) | ✅ **纯粹** |
| `my-mall-product` | `pms` (13) + `cms` (4) | ⚠️ `cms` 归属待定 |
| `my-mall-marketing` | `sms` (13) + **`pms` (1)** | ⚠️ 跨域 1 张 |
| **`my-mall-portal`** | **`oms`(5) + `pms`(8) + `sms`(12) + `ums`(4) + `cms`(1)** | 🔴 **5 个前缀 / 30 张表** |
| `my-mall-search` | **`pms` (3)** | ⚠️ 跨域（只读商品） |

### 2.2 结论

> **`my-mall-portal` 是拆库的最大障碍** —— 它以"聚合前台"的身份**直接访问 5 个模块的 30 张表**。

这正是 **`后期优化文档.md` #12 问题 A（跨域直写）** 的体现，也是拆库必须先解决的问题。

**当前为什么没暴露**：

```
单库 + 本地事务 → 跨域写在同一个事务里，可靠
     ↓
拆库后（阶段 1 起）
     ↓
跨库写【无法用本地事务保证】→ #12 问题 A 立即暴露
```

### 2.3 跨域访问的三种类型（处理方式不同）

| 类型 | 例子 | 拆库后代价 |
|---|---|---|
| **跨域读** | portal 读 `pms_product` 展示商品 | ⚠️ 改 Feign 调用（多一次网络往返） |
| **跨域 JOIN** | portal 的 `oms_order` JOIN `pms_sku_stock` | 🔴 **必须拆分**（跨库无法 JOIN） |
| **跨域写** | portal 写 `pms_sku_stock`（锁库存） | 🔴 **最严重** —— 失去事务保护 |

## 三、目标库划分

### 3.1 五库方案（推荐）

```
mall_user       ← ums_*              （25 张）
mall_product    ← pms_* + cms_*      （18 + 12 = 30 张）
mall_order      ← oms_*              （8 张）
mall_marketing  ← sms_*              （13 张）
mall_portal     ← 无表（纯聚合层）★ 拆库后【不能再直连任何库】
```

**库与服务的关系**：

| 库 | 服务 | 说明 |
|---|---|---|
| `mall_user` | `my-mall-user` | 独占 |
| `mall_product` | `my-mall-product` | 独占（含 cms） |
| `mall_order` | `my-mall-order` | 独占 |
| `mall_marketing` | `my-mall-marketing` | 独占 |
| — | `my-mall-portal` | **纯聚合，通过 Feign 访问上述服务** |
| — | `my-mall-search` | 通过 Feign 读商品 |
| — | `my-mall-file` / `gateway` / `auth` | 无表 |

### 3.2 `cms_*` 的两种归属

| 选项 | 做法 | 评价 |
|---|---|---|
| **A. 跟 `pms_*`**（当前状态） | `mall_product` 库包含 cms | ✅ **改动最小**（product 服务已在访问） |
| **B. 独立 `mall_cms` 库 + 新服务** | 拆出 `my-mall-cms` | ⚠️ 表少（12 张）、价值低，**除非业务独立演进** |

**建议 A** —— cms 与商品强相关（专题/话题都关联商品），且 product 服务已在访问。

## 四、拆库顺序（四阶段）

```
                    当前：单库 mall（76 表）
                            │
        ┌───────────────────┴───────────────────┐
        │  阶段 0：消除跨域（★ 必做前置，不动物理库）│
        │    portal 30 张表 → 全部改 Feign         │
        │    marketing 1 + search 3 → 改 Feign    │
        └───────────────────┬───────────────────┘
                            ▼
                    阶段 1：schema 分离（5 库，同实例）
                            │
                            ▼
                    阶段 2：拆实例（每库独立 MySQL）
                            │
                            ▼
                    阶段 3：读库分离（性能优化）
```

### 4.1 阶段 0：消除跨域访问（**不动物理库**）

**目标**：让每个服务**只访问自己的库**。

```
① portal 的 30 张表访问 → 全部改为 Feign 调各服务
     · oms(5)   → 调 my-mall-order
     · pms(8)   → 调 my-mall-product
     · sms(12)  → 调 my-mall-marketing
     · ums(4)   → 调 my-mall-user
     · cms(1)   → 调 my-mall-product
② marketing 的 pms(1) → 调 my-mall-product
③ search 的 pms(3)    → 调 my-mall-product
```

**★ 为什么这一步必须在前**：

| 若先物理拆库 | 若先消除跨域 |
|---|---|
| ❌ 跨库 JOIN 立即失败 | ✅ 物理拆库只是"改数据源配置" |
| ❌ 跨库写失去事务保护 | ✅ 每步可独立验证、可分批 |
| ❌ 大面积故障 | ✅ 风险可控 |

**★ 也是 #12 问题 A 的正解**（跨域写改 Feign + Outbox）。

### 4.2 阶段 1：schema 分离（5 库，同一 MySQL 实例）

```
① 建 5 个库
② 按前缀迁表（mysqldump / INSERT ... SELECT）
③ 各服务改数据源（Nacos 配置，每服务一个 dataId）
④ 去掉跨库 JOIN（阶段 0 已完成，理论上无 JOIN）
⑤ 验证：全链路回归 + 对账
```

**✅ 本阶段优势**：同实例 → **仍可用跨库事务（若需要）+ 无网络延迟增加**。

### 4.3 阶段 2：拆实例（每库独立 MySQL）

```
① 独立连接池、独立主从
② 分布式事务问题浮现 → 用 Outbox + 对账兜底（见第六章）
③ 故障隔离验证（停一个实例看影响面）
```

### 4.4 阶段 3：读库分离（可选，性能优化）

```
① 热点读走从库
② 与 #19 的性能优化协同（热点行锁竞争）
```

## 五、阶段 0 详解：消除跨域访问

### 5.1 portal 的 30 张表访问（最大工作量）

**为什么 portal 会有这么多跨域访问**：

```
portal 是"前台门户"，其职责是聚合展示 + 下单入口：
  · 商品详情页     → 读 pms（商品、SKU、促销）
  · 购物车页       → 读 pms + sms（促销）+ oms（购物车）
  · 订单确认页     → 读 pms + sms + ums（积分）+ oms
  · 下单           → 写 oms + pms（锁库存）+ sms（核销券）+ ums（扣积分）
  · 我的订单       → 读 oms + pms（商品快照）
```

**改造方式（三种）**：

| 方式 | 做法 | 适用 |
|---|---|---|
| **① 改为 Feign 调用** | portal 调各服务的 REST 接口 | ✅ **首选**（语义清晰） |
| **② 数据冗余** | 下单时把商品信息**快照**进 `oms_order_item` | ✅ 用于"我的订单"（**已经不依赖实时商品**） |
| **③ 聚合服务** | 新增 BFF 层聚合 | ⚠️ 复杂，除非前端调用次数过多 |

**★ 关键洞察：`oms_order_item` 已经是快照**

```
oms_order_item 存了：product_name / product_pic / product_price / product_sku_code / ...
  → "我的订单"列表【不需要】再查 pms_*（快照已足够）
  → 这类跨域读可以【直接删除】，无需改 Feign  ← 成本最低
```

**改造优先级**：

| 优先级 | 类型 | 做法 |
|---|---|---|
| **P0** | **跨域写**（锁库存/核销券/扣积分） | 改 Feign 调各域服务（**#12 问题 A**） |
| **P1** | **跨域 JOIN** | 拆成多次单表查询 + 内存组装 |
| **P2** | **跨域读**（实时性要求低） | 优先用快照字段替代；否则改 Feign |

### 5.2 静态扫描（可作为 CI 检查）

本次侦察用的方法 —— **扫描各服务 XML 中的表名，识别跨域**：

```powershell
# 伪代码：对每个服务，提取 XML 中的表前缀，判断是否越界
foreach ($svc in $services) {
    $prefixes = 扫描 $svc 下的 *.xml 中所有 (ums|pms|sms|cms|oms)_\w+
    if ($prefixes 与 $svc 的归属前缀不一致) {
        报告跨域
    }
}
```

**★ 建议**：把这套扫描做成**构建期检查**（越界即失败），防止改造后回退。

### 5.3 search 的跨域（3 张 pms 表）

```
现状：my-mall-search 直连 pms_* 建索引
改造：改为调 my-mall-product 的接口拉取商品数据
     （或走 MQ：商品变更 → 发消息 → search 消费建索引）★ 更主流
```

## 六、跨域写的一致性方案

### 6.1 当前的跨域写点（#12 问题 A）

| 写入点 | 目标域 | 同库时 | 拆库后 |
|---|---|---|---|
| 锁定库存 `pms_sku_stock` | 商品域 | ✅ 本地事务 | ❌ **跨库** |
| 核销券 `sms_coupon_history` | 营销域 | ✅ 本地事务 | ❌ **跨库** |
| 扣积分 `ums_member` | 用户域 | ✅ 本地事务 | ❌ **跨库** |
| 插订单 `oms_order` | 订单域 | ✅ 本地事务 | ✅ 本库 |

### 6.2 三种方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **① 同步 Feign** | portal 调 order 的"下单接口"，order 再调 product/marketing/user | 语义清晰、强一致（失败即拒绝） | 需**补偿机制**（无 2PC） |
| **② Outbox 最终一致** | 订单落库 + 写 outbox 表 → 异步投递 | 高并发、低延迟 | **最终一致**（秒级延迟） |
| **③ Saga 编排** | 定义正向/补偿动作，失败逐步回滚 | 适合长事务 | 复杂度高 |

### 6.3 推荐：**① + ② 混合**

```
【同步路径】下单主流程（必须强一致的环节）
   portal → order 服务「下单」
        → order 服务编排：
             ① 调 product：「锁定库存」（#9 的原子条件更新，天然分布式安全）
             ② 调 marketing：「核销券」（#13 的条件更新）
             ③ 调 user：「扣积分」（#13 的原子扣减）
             ④ 写本库 oms_order + oms_order_item
        → 任一步失败 → 抛异常 → 前序步骤【补偿回滚】（或让对账发现）

【异步兜底】对账机制（#12 已有）
   5 条不变量 + 每日定时任务 → 发现跨域不一致 → 告警
```

**★ 为什么不需要 2PC（两阶段提交）**：

> 因为本项目已有的**原子条件更新范式天然分布式安全** ——
> 它依赖 **InnoDB 行锁**（数据库层），而非 JVM 锁。
> 每个域的写操作**自身是幂等的、可重试的**（按影响行数裁决），
> 因此**用"重试 + 补偿 + 对账"即可**，无需引入 2PC 的复杂性与性能代价。

### 6.4 拆库后必须强化的能力

| 能力 | 现状 | 拆库后 |
|---|---|---|
| **对账** | ✅ `#12` 已实现（5 条不变量 + 定时任务） | 🔴 **价值更大** —— 跨库不一致的**唯一发现手段** |
| **幂等** | ✅ `#14`/`#15-A`/`#16` 已实现 | 🔴 **必需** —— 网络重试、消息重投 |
| **补偿** | ⚠️ 部分（取消订单释放资源） | 🔴 **需要完整化**（Saga 补偿动作） |
| **Outbox** | ❌ 未实现（#10 决定不做） | ⚠️ **推荐补上**（异步路径的可靠投递） |

## 九、总结

### 9.1 核心判断

| 判断 | 依据 |
|---|---|
| **拆库的技术难点不是"建库迁表"** | 那是 DBA 脚本工作 |
| **难点是「消除跨域访问」+「保证跨域一致」** | 实测：portal 访问 **5 个前缀 / 30 张表** |
| **必须"先消除跨域，再物理拆库"** | 否则跨库 JOIN 立即失败、跨库写失去事务保护 |
| **本项目的"原子条件更新"范式天然分布式安全** | 依赖 InnoDB 行锁（DB 层）而非 JVM 锁 → 拆库后无需分布式锁 |

### 9.2 两个已有资产是拆库的关键

| 资产 | 作用 |
|---|---|
| **① 原子条件更新范式**（复用 8 次） | 每个域的写操作**幂等、可重试** → 用"重试+补偿"替代 2PC |
| **② 对账机制**（`#12`，5 条不变量） | 跨库不一致的**唯一发现手段** → 拆库后价值更大 |

### 9.3 路线图（一页速览）

```
阶段 0（前置）  消除跨域：portal 30 张表 + marketing 1 + search 3 → 改 Feign
                ★ 不动物理库、可分批、风险最低、还是 #12 问题 A 的正解
      ↓
阶段 1          建 5 库 + 按前缀迁表 + 改数据源（同实例，仍可用跨库事务）
      ↓
阶段 2          拆实例（分布式事务问题浮现 → Outbox + 对账兜底）
      ↓
阶段 3          读库分离（性能优化，与 #19 协同）
```

### 9.4 一句话

> **拆库的本质不是"把表分到不同库"，而是"把跨域访问改成跨服务调用，并接受最终一致性（用对账兜底）"。**
> **物理拆库是最后一步，消除跨域才是第一步。**
