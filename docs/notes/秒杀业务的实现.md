## 一、秒杀的本质难点

秒杀的本质是**瞬时流量洪峰**与**有限库存**的对抗：

```
1000 件商品，10 万个请求在 1 秒内到达
  → 只有 1000 个请求能成功（0.1%）
  → 999,000 个请求必须被快速拒绝

难点不在"卖出 1000 件"，而在：
  ① 如何让 99.9% 的无效请求【不消耗系统资源】
  ② 如何保证 1000 件【不超卖、不重复卖】
  ③ 如何让用户【快速得到结果】（哪怕是"已售罄"）
```

**三个子问题**：

| 子问题 | 说明 |
|---|---|
| **超卖** | 卖出超过库存（**正确性问题**，见 [库存超卖与乐观锁原理](库存超卖与乐观锁原理.md)） |
| **热点** | 所有请求抢同一行数据 → **串行化排队**（**性能问题**，即 #19） |
| **雪崩** | 洪峰打垮数据库/服务 → **可用性问题** |

## 二、为什么常规下单扛不住秒杀

本项目当前的下单流程（`OmsPortalOrderServiceImpl.generateOrder`，一个事务内 14 步）：

```java
@Transactional(rollbackFor = Exception.class)          // ← 整个方法是一个事务
public Map<String, Object> generateOrder(OrderParam orderParam) {
    //  1. 校验参数
    //  2. 获取购物车促销信息（查 DB）
    // 2.5 原子抢占购物车行（#14 幂等）
    //  3. 校验库存（查 DB）
    //  4. 处理优惠券（查 DB）
    //  5. 处理积分（查 DB）
    //  6. 计算每件商品实付金额
    //  7. 锁定库存          ← ★ 在这里拿到 pms_sku_stock 行锁
    //  8. 计算订单总金额
    //  9. 填充订单信息（含 generateOrderSn → 【Redis 网络调用】）
    // 10. 插入订单表 + 订单明细表（2 次 DB 写）
    // 11. 更新优惠券使用状态（DB 写）
    // 12. 扣除用户积分（DB 写）
    // 13. 删除购物车中已下单商品（DB 写）
    // 14. 发送延迟消息（【RabbitMQ 网络调用】）
}   // ← 事务提交，此时才【释放行锁】
```

**问题定位**：

```
行锁的持有时长 = 第 7 步 → 第 14 步 的全部耗时
               （而不只是那条 UPDATE 的耗时）
               ↑ 包含 2 次远程调用（Redis 发号 + MQ 发消息）
               ↑ 以及 5 次 DB 写
```

## 三、热点库存行锁竞争（#19）

### 3.1 锁点在哪

`#9` 修复后的库存锁定 SQL（`PortalOrderDao.lockStockSafely`）：

```sql
UPDATE pms_sku_stock
SET lock_stock = lock_stock + #{quantity}
WHERE id = #{skuId}
  AND stock - lock_stock >= #{quantity}
```

**InnoDB 会给 `id = #{skuId}` 这一行加排他锁（X 锁），并持有到事务提交**。

> 注：`#9` 修的是**正确性**（用原子条件更新消除丢失更新），但**原子 UPDATE 本身仍要行锁** —— **#9 与 #19 是一体两面**：
> 为了保证不超卖，**必须**加锁；而加锁**必然**串行化。

### 3.2 具体场景举例

```
商品：iPhone 14（SKU 201），秒杀库存 100 件
1000 个用户同时点击"立即抢购"

时刻 T0：1000 个请求同时到达 generateOrder

请求1：拿到 id=201 的行锁 → 执行 UPDATE → 继续走第 8~14 步（含 2 次远程调用）
请求2：想拿行锁 → 【被阻塞】→ 等待
请求3：想拿行锁 → 【被阻塞】→ 排队
...
请求1000：想拿行锁 → 【被阻塞】→ 排队

请求1 走完第 8~14 步 → 事务提交 → 释放行锁
请求2 才拿到行锁 → 执行 UPDATE → 继续走第 8~14 步
（如此串行 1000 次）
```

### 3.3 实测量化

| 测试 | 结果 |
|---|---|
| 单条 `UPDATE pms_sku_stock SET lock_stock=...`（无竞争） | **0.05 ms** |
| 1000 条串行 `UPDATE`（理想情况，不含后续步骤） | **51 ms** |

**推演真实情况**：

```
若每个请求"第7~14步"总耗时 = X ms
则 1000 并发请求的排队总时长 ≈ 1000 × X

保守估计 X = 10ms（2 次远程调用 + 5 次 DB 写）：
  1000 × 10ms = 10,000 ms = 10 秒
  → 最后一个用户要等 10 秒

若 RabbitMQ 响应抖动到 500ms：
  1000 × 500ms = 500 秒 → 用户必然超时
```

**对比**：若只锁"UPDATE 那一下"（不拉长事务），1000 请求仅需 **51 ms** —— **差了约 200 倍**。

### 3.4 两个放大因素

| 因素 | 影响 |
|---|---|
| **① 热点集中** | 秒杀时所有请求抢**同一个 SKU 行** → 行锁**完全串行化**，无法并行 |
| **② 持锁时间长** | 事务跨越第 7~14 步，含 **2 次远程调用 + 5 次 DB 写**；**网络调用最不可控**（抖动/超时可达数百 ms） |

## 四、主流方案：四层防御体系

**核心思路不是"去掉锁"，而是**：

> **把"锁"从慢介质（MySQL）挪到快介质（Redis），并把"同步串行"变成"异步削峰"。**

### 第 1 层：流量层 —— 挡住 90% 的请求

| 手段 | 说明 |
|---|---|
| **限流**（令牌桶/漏桶） | 秒杀瞬间只放行 N 个请求 |
| **验证码 / 答题** | 强制人机交互，拖慢脚本 |
| **前端按钮置灰 + 倒计时** | 未开始不能点 |
| **虚拟排队页** | 进入前先"排队"，削峰 |
| **用户维度限流** | 一人一单，挡掉重复请求 |

> 典型案例：小米/华为商城秒杀 —— 点击后进入"排队中"页面，**不是立即返回结果**。

### 第 2 层：库存层 —— 把库存挪到 Redis（**核心**）

```
MySQL 扣减：单条 0.05ms，但 + 网络 + 事务 → 实际 10~50ms/次，且【串行】
Redis 扣减：0.01ms，单机 10 万+ QPS，纯内存、单线程【无锁竞争】

→ 主流：库存放 Redis，用 Lua 脚本原子扣减
```

### 第 3 层：下单层 —— 异步化削峰

```
同步下单（本项目现状）：
  用户请求 → 锁库存 → 写订单 → 写明细 → 写券 → 写积分 → 返回
  ↑ 用户要等完整流程（几十~几百 ms）

异步下单（主流秒杀）：
  用户请求 → Redis 扣库存 → 发 MQ → 【立即返回"排队中"】
                                    ↓
                          消费者异步：写订单 + 写明细 + ...
  ↑ 用户只等 Redis 扣减（~1ms）
```

### 第 4 层：数据库层 —— 兜底 + 最终一致性

Redis 预扣减之后，**数据库仍需最终落库**：

| 手段 | 说明 |
|---|---|
| **MQ 异步落库** | 消费者把"预扣减"真正写入 DB |
| **定时对账** | 比对 Redis 与 DB 差异并修正（本项目 **#12 已做对账**） |
| **超时回补** | 未支付订单，把库存加回 Redis |
| **DB 层原子 UPDATE** | `WHERE stock >= n` 双保险（本项目 **#9 已做**） |

## 五、三种主流架构方案对比

### 方案 A：Redis 预扣减 + MQ 异步落单（大厂主流）

```
用户 → [限流] → [Redis Lua 扣库存] → [发 MQ] → 返回"排队中"
                                        ↓
                                [消费者] → [DB 写订单]
```

| 维度 | 评价 |
|---|---|
| 并发能力 | ✅ **10 万+ QPS** |
| 超卖风险 | ✅ 低（Redis 原子 + DB 兜底） |
| 复杂度 | ⚠️ 高（Redis/DB 一致、消息可靠性、幂等） |
| 响应语义 | ❌ **变为异步**（返回"排队中"而非订单号） |
| 典型用户 | 淘宝、京东、拼多多、小米商城 |

### 方案 B：库存分段（分桶）—— 不改语义，纯提性能

```
1000 件库存 → 拆成 10 段，每段 100 件

请求1 → 打到 seg_1 的行锁
请求2 → 打到 seg_3 的行锁      ← ★ 不同行 = 不阻塞
请求3 → 打到 seg_7 的行锁
...
→ 原本 1 行锁串行，变成 10 行锁并行
```

| 维度 | 评价 |
|---|---|
| 并发能力 | ✅ 提升 N 倍（N = 分段数） |
| 超卖风险 | ✅ 无（每段独立原子扣减） |
| 响应语义 | ✅ **不变**（仍同步返回） |
| 复杂度 | ⚠️ 中（需维护分段表 + 汇总查询） |
| 缺点 | ⚠️ 段粒度难定（太大竞争仍高，太小汇总复杂） |

### 方案 C：缩短事务 —— 改动最小

```
把事务外的操作移出去：
  · Redis 发号     → 移出事务（或改 DB 序列）
  · MQ 发消息      → 事务提交后（afterCommit / Outbox）
合并多次 DB 写：
  · 明细批量 insert（本项目已做 insertList）
```

| 维度 | 评价 |
|---|---|
| 并发能力 | ⚠️ 提升有限（减少持锁时长，但仍串行） |
| 超卖风险 | ✅ 无 |
| 响应语义 | ✅ **不变** |
| 复杂度 | ✅ **低** |

> **这就是本项目 `后期优化文档.md` 中 #19 的方案①。**

## 六、核心实现：Redis + Lua 原子扣减

### 6.1 为什么必须用 Lua

**Redis 单条命令是原子的，但"读-判断-写"是三条命令，非原子**：

```
❌ 错误写法（三条命令，中间可被其他请求插入）：
  GET  stock          → 100
  if (100 > 0) {      ← 两个请求都可能判断通过
     DECR stock       → 99
  }
  → 超卖

✅ 正确写法（Lua 脚本，Redis 单线程原子执行）：
  Lua 脚本内的所有命令作为一个整体执行，中间不会插入其他命令
```

### 6.2 Lua 脚本

```lua
-- 库存预扣减
-- KEYS[1] = 库存 key，如 seckill:stock:201
-- 返回：1 = 扣减成功；0 = 已售罄；-1 = 商品不存在

local stock = tonumber(redis.call('GET', KEYS[1]))
if stock == nil then
    return -1                      -- 商品不存在（或未初始化）
end
if stock <= 0 then
    return 0                       -- 已售罄
end
redis.call('DECR', KEYS[1])
return 1                           -- 扣减成功
```

> **若需支持"一次扣多件"**，把 `DECR` 改成 `DECRBY KEYS[1] ARGV[1]`，并在判断里用 `stock < ARGV[1]`。

### 6.3 Java 调用

```java
private static final DefaultRedisScript<Long> SECKILL_SCRIPT = 
    new DefaultRedisScript<>(SECKILL_LUA, Long.class);

public void seckill(Long skuId, Long memberId) {
    String stockKey = "seckill:stock:" + skuId;

    Long result = redisTemplate.execute(
            SECKILL_SCRIPT,
            Collections.singletonList(stockKey));

    if (result == null) {
        throw new BusinessException("秒杀失败，请重试");
    }
    if (result == -1) {
        throw new BusinessException("商品不存在");
    }
    if (result == 0) {
        throw new BusinessException("已售罄");
    }
    // 扣减成功 → 发 MQ 异步创建订单
    seckillOrderSender.send(skuId, memberId);
}
```

### 6.4 为什么 Redis 快（对比表）

| 维度 | MySQL 行锁 | Redis Lua |
|---|---|---|
| 存储介质 | 磁盘（+ Buffer Pool） | **纯内存** |
| 并发模型 | 行锁 → **串行排队** | 单线程 → **无锁**，天然原子 |
| 单次耗时 | 0.05ms（纯 SQL），实际 10~50ms（含事务/网络） | **~0.01ms** |
| 单机 QPS | 数千 | **10 万+** |
| 事务开销 | undo/redo log、MVCC | 无 |

**差距约 2~3 个数量级** —— 这是主流方案把库存搬到 Redis 的根本原因。

## 七、核心实现：异步下单与结果轮询

### 7.1 响应语义的变化（关键）

| | 同步下单（本项目现状） | 异步下单（主流秒杀） |
|---|---|---|
| 响应 | `{"code":200,"orderSn":"20261016..."}` | `{"code":200,"msg":"排队中","token":"xxx"}` |
| 用户后续 | 直接看到订单 | **轮询 `/seckill/result?token=xxx`** |
| 系统耗时 | 完整流程（几十~几百 ms） | **仅 Redis 扣减（~1ms）** |

### 7.2 典型流程

```
① 用户点击"立即抢购"
      ↓
② 服务端：限流检查（一人一单、令牌桶）
      ↓
③ Redis Lua 原子扣库存
      ↓ 成功
④ 生成唯一 token → 存入 Redis（token → 处理中状态）
      ↓
⑤ 发 MQ 消息（含 token、skuId、memberId）→ 【立即返回"排队中"】
      ↓
   ┌─────────── MQ 消费者（异步）───────────┐
   │ ⑥ 校验幂等（同一 token 只处理一次）      │
   │ ⑦ DB 写订单 + 明细 + 券 + 积分          │
   │ ⑧ 更新 token 状态为"成功"（含订单号）    │
   │ ⑨ 失败则回补 Redis 库存                 │
   └────────────────────────────────────────┘
      ↓
⑩ 前端轮询 /seckill/result?token=xxx → 拿到结果
```

### 7.3 消费者的幂等（必做）

```java
// 同一 token 只处理一次：用 SETNX 或 DB 唯一索引
Boolean first = redisTemplate.opsForValue()
        .setIfAbsent("seckill:consumed:" + token, "1", 10, TimeUnit.MINUTES);
if (Boolean.FALSE.equals(first)) {
    return;   // 已处理过，直接跳过
}
```

> **本项目已有同类经验**：
> - `#14` 用"抢占购物车行"实现下单幂等
> - `#16` 用"`UPDATE ... WHERE status=0`"实现支付幂等
> - 手法同款：**把检查并入写操作，按影响行数裁决**

## 八、库存最终一致性保障

Redis 预扣减后，**Redis 与 DB 之间必然存在短暂不一致**，必须兜底：

| 机制 | 说明 | 本项目情况 |
|---|---|---|
| **DB 原子 UPDATE** | 消费者写 DB 时仍用 `WHERE stock-lock_stock >= n` 双保险 | ✅ **#9 已做** |
| **定时对账** | 比对 Redis 与 DB 库存差异，告警/修正 | ✅ **#12 已做对账（5 条不变量）** |
| **超时回补** | 未支付订单到期后，库存加回 Redis 与 DB | ✅ **#15-A / #10 已做取消释放** |
| **消息可靠性** | MQ 消息不丢（Outbox / 确认机制） | ⚠️ **#10 讨论过，用户决定暂不做** |

**特别提醒：不能只信 Redis，也不能只信 DB**

```
只信 Redis：Redis 宕机/重启 → 库存数据丢失 → 超卖
只信 DB   ：DB 行锁竞争 → 就是 #19 的问题

→ 主流答案：Redis 做"快速过滤"，DB 做"最终裁决"，对账做"差异修正"
```

## 九、本项目现状对照

| 层次 | 主流做法 | 本项目现状 | 说明 |
|---|---|---|---|
| **流量层** | 限流 + 验证码 + 排队 | ❌ **无** | 迁移期不做 |
| **库存层** | Redis 预扣减 | ❌ **用 DB 行锁** | #9 的方案（保证正确性） |
| **下单层** | MQ 异步削峰 | ❌ **同步下单** | 需改变响应语义 |
| **DB 层** | 原子 UPDATE + 对账兜底 | ✅ **已做** | #9 原子更新 + #12 对账 |

**结论**：本项目的**正确性防线已经完备**（`#9` 原子扣减 + `#12` 对账 + `#14`/`#16` 幂等），
但**性能架构仍是"传统同步"**。

**为什么现在不做**：

> **迁移期要求"与老服务逐字节一致"**。
> 改成 Redis 预扣减 / 异步下单，**响应语义会变**（返回"排队中"而非订单号），
> **这违反迁移纪律**。

## 十、演进路径（分阶段）

```
┌─ 阶段 1（当前）：DB 行锁 + 原子 UPDATE + 对账
│    适用：无秒杀、并发 < 1000
│    本项目：#9 + #12 已完成 ✅
│
├─ 阶段 2：缩短事务（#19 方案①）
│    做法：Redis 发号、MQ 发消息移出事务（afterCommit / Outbox）
│    适用：并发 1000 ~ 5000
│    特点：✅ 改动小、✅ 不破坏契约
│    前置：需先解决 #10 的可靠投递（否则消息会丢）
│
├─ 阶段 3：库存分段（方案 B）
│    做法：库存拆 N 段，各自独立扣减；查询时 SUM 汇总
│    适用：并发 5000 ~ 5 万
│    特点：✅ 响应语义不变；⚠️ 需改表结构 + 扣减逻辑 + 查询
│
├─ 阶段 4：Redis 预扣减 + MQ 异步（方案 A）
│    做法：Redis Lua 扣库存 → 发 MQ → 返回"排队中" → 消费者落库
│    适用：真秒杀，10 万+ QPS
│    特点：❌ 响应语义改变；⚠️ 复杂度高
│
└─ 阶段 5：独立秒杀服务
     做法：秒杀与主站隔离（独立部署、独立 DB、独立 Redis）
     特点：故障隔离，秒杀挂掉不影响主站
```

### 触发条件对照表

| 并发规模 | 该做哪一步 | 是否需要改响应语义 |
|---|---|---|
| < 1,000 | 阶段 1（现状即可） | ❌ 不用 |
| 1,000 ~ 5,000 | **阶段 2**（缩短事务） | ❌ 不用 |
| 5,000 ~ 50,000 | 阶段 3（库存分段） | ❌ 不用 |
| > 50,000 | 阶段 4（Redis + 异步） | ✅ **需要** |
| 真秒杀业务 | 阶段 5（独立服务） | ✅ 需要 |

> **重要提示**：阶段 2 和 3 **都不改变响应语义**，因此在"与老服务对齐"的约束下**也是可以做的**；
> 只有阶段 4 起才必须改变语义。

## 十一、总结

### 核心矛盾

```
不超卖 → 必须"检查+扣减"原子 → 必须加锁
加锁   → 同一行串行化        → 并发越高排队越久
```

### 主流的破解方式

> **不是"去掉锁"，而是"把锁从慢介质挪到快介质、把同步改成异步"**：

| 层次 | 手段 | 效果 |
|---|---|---|
| **流量层** | 限流 / 验证码 / 排队 | 挡掉 90%+ 请求 |
| **库存层** | **Redis + Lua 原子扣减** | 从 MySQL 行锁（10ms 串行）→ Redis（0.01ms 无锁） |
| **下单层** | **MQ 异步落单** | 用户只等 Redis 那一下 |
| **DB 层** | 原子 UPDATE + 对账兜底 | 保证最终一致（**本项目已做**） |

### 代价

**响应语义从"同步返回订单"变成"异步返回排队中"**。

### 对本项目的结论

| 问题 | 结论 |
|---|---|
| **现在要做吗** | ❌ **不做** —— 无秒杀业务，且改响应语义违反迁移纪律 |
| **若将来要做** | 从**阶段 2（缩短事务）**起步 —— **改动最小且不破坏契约** |
| **现阶段该做什么** | ✅ 保证**正确性**（`#9` 原子扣减、`#12` 对账、`#14`/`#16` 幂等）—— **已完成** |

> **正确性可以慢慢演进性能，但正确性错了就是资损。**
> 本项目先把"不超卖、不重复、可对账"做扎实，性能架构留待真实流量驱动。
