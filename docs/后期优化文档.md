#### 1. 库存超卖风险　✅ **已由 #9 覆盖（2026-10-15 核实，无需改代码）**

> **核实结论**：本条被 **#9（锁库存丢失更新）** 完整覆盖，且**实现方式比本条建议更符合项目的库存三步曲模型**。
> **实验证据**：修复前 9 并发抢 5 件 → 成功 **9 单（超卖 4 件）**；修复后 → **成功 5 单（零超卖）**。

**问题：**
```java
cartPromotionItem.setRealStock(skuStock.getStock() - skuStock.getLockStock());
```
只是展示用，没有加锁。高并发下多个用户同时看到有库存，都下单成功，导致超卖。

**★ 为什么不用本条建议的 SQL（语义差异）**

| | 文档建议 | **我们的实现（#9 `lockStockSafely`）** |
|---|---|---|
| SQL | `SET stock = stock - qty, lock_stock = lock_stock + qty WHERE stock >= qty` | `SET lock_stock = lock_stock + qty WHERE stock - lock_stock >= qty` |
| 语义 | **下单即扣 `stock`** | **下单只加 `lock_stock`；支付成功才扣 `stock`** |
| 评价 | ⚠️ 与项目三步曲模型**冲突** | ✅ **正确** |

**项目的库存三步曲**（老项目行为，迁移纪律要求一致）：
```
下单（未付款） → stock 不变，lock_stock +1   「占住，不扣」
支付成功       → stock -1，lock_stock -1     「真扣」
取消/超时      → stock 不变，lock_stock -1   「释放」
```
若按文档"下单即扣 stock"，则**取消订单时必须加回 stock** —— 会破坏整个模型，且与老项目行为不一致。

**★ 关键澄清：`realStock` 是「只读快照」，本就不需要锁**

| 环节 | 代码 | 性质 |
|---|---|---|
| **展示**（购物车/确认单看库存） | `setRealStock(stock - lockStock)` | **只读快照 —— 不需要锁，也锁不住** |
| **真正的扣减**（下单锁库存） | `lockStockSafely(...)` | ✅ **已有原子守卫**（#9 已修） |

用户看到"有货"不代表一定能买到 —— **真正的守门人在下单环节**（用 `stock - lock_stock >= quantity` 原子判定）。本条把"展示"与"扣减"混为一谈了。

**涉及文件：** 下单Service（`OmsPortalOrderServiceImpl.lockStock`）、`PortalOrderDao.xml` —— **均已在 #9 中完成**

// ① SQL 补查时间列（PromotionProduct extends PmsProduct，字段已存在但原 SQL 未查 → null）
SELECT p.id, p.name, p.promotion_type,

// ③ 判断逻辑：NULL 表示"不限制"，不计为过期
private boolean isPromotionInEffect(PromotionProduct p) {

    if (p.getPromotionEndTime()   != null && now.after(p.getPromotionEndTime()))   return false;

**为什么选 Service 层而非文档建议的 SQL 层过滤**：

#### 4. 满减分摊精度问题　✅ **已完成（2026-10-16）**

> **修复结果**：商品 28（满 1000 减 120）买 649+699+649（总价 1997）—— 修复前 `promotionAmount=118.80`、`payAmount=1878.20`（**用户多付 1.20 元**）；修复后 **`promotionAmount=120.0000`、`payAmount=1877.00`**。下单全链路三处金额完全一致。
> **改动**：`calcFullReductionPromotion` 改为"最后一行补齐" + 按行小计分摊 + 显式 scale。
> **证据**：`mall-work\stress\result\evidence-fullreduction.txt`。

**问题：**
满减按比例分摊到每件商品，用 `divide(totalAmount, RoundingMode.HALF_EVEN)` 可能出现分摊后合计不等于满减金额（四舍五入误差）。

**★ 实测确认（问题真实，且误差直接落到用户实付）**

```
商品 28 小米红米5A（满1000减120）
加购：SKU 102(649) + 103(699) + 104(649)，总价 = 1997

promotionMessage = "满减优惠：满1000.00元，减120.00元"   ← 承诺减 120
各件分摊：0.32×120 + 0.35×120 + 0.32×120
         = 38.40 + 42.00 + 38.40 = 118.80
promotionAmount = 118.8000        ← 实际只减 118.80
payAmount       = 1878.2000
★ 差额 1.20 元 —— 用户看到的优惠是 120，实际多付 1.20
```

**根因**：`divide` **未指定 scale** → 用 `totalAmount.scale()`（=2）→ `649/1997 = 0.325...` 被截成 **`0.32`** → **每件都舍入一次，误差随件数放大**。

**另用 Java 精确模拟印证**：总价 300、满减 30、三件各 100 → `0.33×30×3 = 29.70`，**差 0.30**。

**金额流向（说明影响面）**：
```
reduceAmount
  → orderItem.promotionAmount
  → calcPromotionAmount（Σ reduceAmount × quantity）
  → order.promotionAmount
  → order.payAmount                    ← 误差直接落到用户实付
```

**优化方案（已实施：最后一行补齐）**

```java
BigDecimal allocated = BigDecimal.ZERO;
int lastIndex = itemList.size() - 1;

for (int i = 0; i <= lastIndex; i++) {
    int quantity = ...;
    BigDecimal quantityDec = new BigDecimal(quantity);

    BigDecimal rowReduce;
    if (i == lastIndex) {
        // ★ ① 最后一行用减法补齐 → 吸收所有舍入误差，合计必然精确等于满减额
        rowReduce = fullReduction.getReducePrice().subtract(allocated);
    } else {
        // ★ ② 按【行小计】(单价×数量) 分摊，scale 显式取 4 位
        BigDecimal rowAmount = originalPrice.multiply(quantityDec);
        BigDecimal ratio = rowAmount.divide(totalAmount, 4, RoundingMode.HALF_EVEN);
        rowReduce = ratio.multiply(fullReduction.getReducePrice());
        allocated = allocated.add(rowReduce);
    }
    // ★ ③ 还原为「每件优惠」（字段语义，订单汇总时会再乘 quantity）
    BigDecimal reduceAmount = rowReduce.divide(quantityDec, 4, RoundingMode.HALF_EVEN);
    ...
}
```

**★ 实现中发现并修正的 bug（重要）**：文档原方案直接对 `originalPrice`（单价）做比例分摊 —— 但核对 `calcPromotionAmount` 后发现它会 `reduceAmount × quantity`，即 **`reduceAmount` 的字段语义是"每件优惠"，不是"该行总额"**。因此必须：
1. 按 **行小计**（单价×数量）比例分摊；
2. 分摊后再 **÷ 数量** 还原为"每件优惠"。

否则**多件商品会算错**（F2/F3 专门验证此点）。

**验证（全 PASS）**：

| # | 场景 | 修复前 | 修复后 |
|---|---|---|---|
| **F1** | 649+699+649（总价 1997，满减 120） | **118.80** ❌ | **120.0000** ✅（明细 39.00+42.00+39.00） |
| **F2** | 102×2 + 103×1（多件混合） | — | **120.0000** ✅ |
| **F3** | 102×3（单行多件，总价 1947） | — | **120.0000** ✅ |
| **F4** | 满 500 减 50（649×1） | — | **50.0000** ✅ |
| **F5** | **下单全流程**：确认单 → 订单表 → 明细 | — | **三处完全一致**（120.00 / 1877.00）✅ |
| **F6** | 回归：#3 促销过期判断 | — | 26/29/45 仍"无优惠" ✅ |

**★ 老项目核对**：`mall-swarm` 的实现**完全相同** → 属"照抄老项目"继承的既有缺陷。

**★ 验证方法**：先用 `javac` 做 **BigDecimal 语义精确模拟**（快速验证算法正确性），再用**真实接口**复验 —— 两种手段结合。

#### 5. 多表JOIN笛卡尔积　⏸ **暂不处理（2026-10-16 实测评估，附行动阈值）**

> **实测结论**：当前**无需优化** —— 实测查询耗时 **0.38~0.9 毫秒**（微秒级），笛卡尔积仅 **12 行**（最大商品），去重成本可忽略。**且实测发现：文档原方案（拆查询）会让性能变差**。

**问题：**
`getPromotionProductList` 三个 LEFT JOIN（sku + ladder + full_reduction），一个商品10个SKU + 3个阶梯 + 2个满减 = 60行，MyBatis去重合并。

**★ 实测数据（2026-10-16）**

**① 当前性能（真实测量）**

| 项 | 实测值 |
|---|---|
| 查询耗时（profiling，5 次） | **0.588 ~ 0.908 毫秒** |
| 笛卡尔积实际行数（商品 37，12 SKU） | **12 行** |
| 数据规模 | 商品 **38** / SKU **95** / 阶梯 **35** / 满减 **36** |

**② `EXPLAIN` 揭示的真正瓶颈（不是笛卡尔积）**

```
当前执行计划（三张表都没有 product_id 索引）:
  p        type=const  rows=1     ✅ 走主键
  sku      type=ALL    rows=96    ⚠ 全表扫描
  ladder   type=ALL    rows=35    ⚠ 全表扫描
  full_re  type=ALL    rows=36    ⚠ 全表扫描

加 product_id 索引后:
  sku      type=ref    rows=12    ✅ 走索引
  ladder   type=ref    rows=1     ✅ 走索引
  full_re  type=ref    rows=1     ✅ 走索引
```

**真正的问题是「缺 `product_id` 索引 → 三张表全表扫描」**，而非"笛卡尔积"。

**③ 全表扫描成本模型（建测试表实测，4 个规模点）**

| 行数 | 全表扫描耗时 | 单位成本 |
|---|---|---|
| 1,024 | 0.32 ms | 0.31 μs/行 |
| 16,384 | 2.31 ms | 0.14 μs/行 |
| 131,072 | 16.84 ms | 0.13 μs/行 |
| 524,288 | 71.77 ms | 0.14 μs/行 |

**→ 严格线性：约 `0.137 微秒/行`**（据此可推算任意规模的扫描成本）

**④ A/B 对照实验（加索引前 vs 后）**

| 状态 | 第 1 次 | 第 2 次 | 第 3 次 |
|---|---|---|---|
| **无索引** | 0.607 ms | 0.446 ms | 0.381 ms |
| **加索引** | 0.653 ms | 0.575 ms | 0.539 ms |

**⚠️ 意外结果：当前数据量下「加索引」反而略慢**（已清理临时索引，未改动表结构）。
**原因**：小表的全表扫描绝对值极低（都在内存页内），而走索引需"查索引 + 回表"，**比直接扫描小表更贵** —— **MySQL 优化器在小表上故意选全表扫描，它的判断是对的**。

**★ 届时应做的：加 `product_id` 索引（不是拆查询）**

| 方案 | 成本 | 实测效果 |
|---|---|---|
| **加 `product_id` 索引** | 1 条 DDL，秒级 | 扫描行数从 N → 该商品 SKU 数（约 12） |
| **拆成 4 次单表查询**（文档原方案） | 改代码 + **多 3 次网络往返** | ⚠️ **往返成本 > 节省的扫描成本 → 更慢** |

**为什么拆查询会更慢**：当前 1 次 SQL 往返（0.4~0.9ms，含网络），拆后变 4 次往返。在真实网络（1~5ms/往返）下，**多出的 3 次往返远超节省的扫描成本**。

**优化方案（已实施，与文档原方案不同）：**

| | 文档原方案①唯一索引 | 文档原方案②分布式锁 | **实采：条件插入** |
|---|---|---|---|
| 做法 | 加 `(coupon_id, member_id)` 唯一索引 | Redis 分布式锁 | `INSERT ... SELECT ... FROM DUAL WHERE 已领数 < per_limit` |
| 问题 | ❌ **只能"一人一张"**，与"限领 N 张"冲突 | ✅ 可行但较重 | ✅ 单条原子，不改表结构 |

**为什么否决唯一索引**：实际 `per_limit` 分布为 **1（券29/30）、5（券28/31）、10（券27）**，唯一索引会把"限领 5 张/10 张"错误收紧为"限领 1 张"，改变业务语义。

```xml
<insert id="insertIfUnderLimit">
    INSERT INTO sms_coupon_history (coupon_id, member_id, coupon_code, ...)
    SELECT #{couponId}, #{memberId}, #{couponCode}, ...
    FROM DUAL
    WHERE (SELECT COUNT(*) FROM sms_coupon_history
           WHERE coupon_id = #{couponId} AND member_id = #{memberId})
          < (SELECT per_limit FROM sms_coupon WHERE id = #{couponId})
</insert>
```

**⚠️ 局限（如实记录）**：InnoDB 默认 REPEATABLE READ 下，并发事务的 `COUNT(*)` 子查询可能读到同一快照，**毫秒级窗口仍可能超领**。此方案的价值在于把竞态窗口从"先查后写"的**整个方法跨度**压缩到"单条语句"的**瞬间**。若要**严格兜底**：
- `per_limit = 1`：可加唯一索引 `(coupon_id, member_id)`；
- `per_limit > 1`：需"领取序号列 + 唯一索引 `(coupon_id, member_id, seq)`"或分布式锁。

#### 11. 延迟队列队头阻塞（TTL 方案固有缺陷）　✅ **已完成（2026-10-16，采用兜底补偿方案）**

**问题：**
`CancelOrderSender` 用**消息级 TTL**（`setExpiration`）投到同一个 TTL 队列。RabbitMQ 只在**队头**判断过期：队首消息 TTL 15 分钟未到期时，它后面那条 TTL 1 秒的消息**也不会被投递**，要等队首过期才一起走。订单取消的准点性随队列深度劣化。

**★ 实测确认（问题真实，且配置上已具备触发条件）**

```
CancelOrderSender：message.getMessageProperties().setExpiration(String.valueOf(delayTimes));  ← 消息级 TTL
RabbitMqConfig   ：单一 TTL 队列 + 死信转发
                   QueueBuilder.durable("mall.order.cancel.ttl")
                       .withArgument("x-dead-letter-exchange", "mall.order.direct")

RabbitMQ 实测：
  mall.order.cancel      messages=0  ready=0  consumers=1
  mall.order.cancel.ttl  messages=1  ready=1  consumers=0   ← 消息卡在 TTL 队列

触发条件已具备（超时配置不同）：
  normal_order_overtime = 120 分钟
  flash_order_overtime  =  60 分钟    ← 两者不同
  → 若同时存在两类订单：普通订单消息（TTL=2h）占队首时，秒杀订单消息（TTL=1h）会被堵住
  → 秒杀订单的库存锁定多占用 1 小时
```

**优化方案（已实施：兜底补偿）**

```java
// OrderTimeOutCancelTask
@Scheduled(cron = "0 0/2 * ? * ?")     // 原为 "0 0/10 * ? * ?"

```

|---|---|---|---|
| **① 兜底频率调高（实采）** | 改 1 个 cron | **极小**，无运维改动 | ✅ **用更勤的扫描补偿准点性** |

| 原先描述 | 实际情况 |
|---|---|

**✅ #15-B 第①②项已完成（2026-10-15）—— `rollbackFor` 与全局默认**

> **修复结果**：A/B 对照实验（同代码、同受检异常、唯一变量是注解）—— **带 `rollbackFor` 的写入被回滚（`0→0`）**，**裸 `@Transactional` 的写入被提交（`0→1`）**；回归 6 项全 PASS。
> **改动**：显式声明 2 处（取消链路）+ 批量补齐 22 处 = **24 处已配，裸注解 0 处**。
> **证据**：`mall-work\stress\result\evidence-rollbackfor.txt`；台账 `replace-log.md` 2026-10-15 行。

**问题**：Spring 的 `@Transactional` **默认只对 `RuntimeException` 回滚**，受检异常（`Exception`/`SQLException`/`IOException` 等）**不回滚但仍提交**。取消链路是「关单 → 释放库存 → 退券 → 退积分」顺序执行的 —— 中间抛受检异常就会留下"**库存已释放、券已退、但订单还是待付款**"的半成品状态。

**★ 方案变更：全局配置不可行（已撤回）**

| 尝试的路 | 结果 |
|---|---|
| 自定义 `TransactionInterceptor` Bean | ❌ 与 Spring Boot 自动配置的**同类型 Bean 冲突** → `BeanFactoryTransactionAttributeSourceAdvisor` 注入时有 2 个候选 → **启动失败** |

#### 17. 前台取消订单接口冗余且实现错误

**问题：**
原项目 portal（前台）存在两个取消订单接口，实现不一致：

| 接口 | summary | 调用方法 | 实际效果 |
|---|---|---|---|
| `POST /cancelOrder` | 取消单个超时订单 | `sendDelayMessageCancelOrder(orderId)` | 发延迟消息，60分钟后才取消 ❌ |
| `POST /cancelUserOrder` | 用户取消订单 | `cancelOrder(orderId)` | 立即取消 ✅ |

具体问题：
1. **`/cancelOrder` 实现错误**：用户/管理员点取消却调用 `sendDelayMessageCancelOrder`，读取 `normalOrderOvertime`（如60分钟）作为延迟时间，导致点了取消后要等60分钟才真正释放库存、券、积分，期间库存仍被锁定；
2. **前台语义不合理**：`/cancelOrder` 的 summary 是"取消单个超时订单"，这是后台管理员视角，前台用户不会有"取消超时订单"这种操作；
3. **接口冗余**：两个接口底层都应该是"立即取消订单"，`/cancelOrder` 属于历史遗留（早期实现写错，后来加了 `/cancelUserOrder` 修正，但旧接口没删）。

**优化方案：**
① 前台**只实现 `/cancelUserOrder`** 作为用户取消订单接口，直接调用 `cancelOrder(orderId)` 立即取消，**不实现 `/cancelOrder`**（原项目的错误冗余接口不需要1:1照抄）；
② 若保留 `/cancelOrder`，必须改为也调用 `cancelOrder(orderId)` 立即取消，不能再发延迟消息；
③ 取消逻辑必须幂等：`UPDATE oms_order SET status=4 WHERE id=? AND status=0`，影响行数=0直接返回（已取消/已支付的订单不能重复取消）；
④ 真正的"超时自动取消"由 MQ 延迟队列 + 定时任务兜底完成，不需要暴露前台接口手动触发。

**涉及文件：** OmsPortalOrderController（只保留 cancelUserOrder）、OmsPortalOrderServiceImpl.cancelOrder/sendDelayMessageCancelOrder

- 下单成功后立刻 `kill 8092` 或断开 RabbitMQ → 重启后观察该订单是否被取消

### 4. 重复提交演练（证明幂等缺口）

## 七、通用优化方向

### 1. 分布式锁
秒杀、领券、扣库存等并发场景，用 Redis 分布式锁（Redisson）。
> 注意：能靠 **DB 条件更新（乐观锁）** 解决的（如 #9 锁库存、#7 领券），优先用 DB，不要引入分布式锁——锁会带来超时、续期、死锁与性能开销。

### 2. 异步处理
- 下单成功后发MQ，异步扣库存、减优惠券、加积分
- 订单超时取消用延迟队列
> 注意：**异步化会改变响应语义**（"下单成功"→"受理中"），与老服务逐字节对齐期间禁止；且必须先解决 #10（消息与 DB 的原子性/Outbox）。

### 3. 缓存
- 商品促销信息缓存到 Redis，减少数据库查询
- 优惠券信息缓存，领券时更新缓存
> 注意：库存类数据**不要缓存**（实时性要求高，会放大超卖）。

### 4. 限流
- 秒杀接口限流，防止恶意刷接口
- 领券接口按用户限流

### 5. 最终一致性（交易域新增）
- **本地消息表（Outbox）** 替代"直接发 MQ"：同库同事务写待投递记录 → 定时投递 + 重试 + 去重
- 消费端**幂等**：状态机条件更新（`WHERE status=0`）+ 唯一索引兜底
- **定时对账**：订单实付 vs 各域扣减记录，发现差异告警并回补

### 6. 事务边界（交易域新增）
- **缩短事务**：只包 DB 写；远程调用（Feign）、MQ 发送、缓存操作移到事务外
- MQ 发送放 `afterCommit`（`TransactionSynchronizationManager`），避免"消息先到数据后到"
- 单库阶段用本地 `@Transactional` 即可；**拆库后才考虑** Seata/Outbox 等分布式方案

### 7. 压测与观测（交易域新增）
- 用 JMeter/wrk 做并发下单、领券压测，**先证明问题存在**再优化
- 关键链路加指标：下单成功率、库存负余量次数、消息投递延迟、取消订单数
- 每项优化都要留"优化前 / 优化后"实测对比，可回滚

## 八、架构演进：数据所有权与拆库路线（2026-10-11 新增）

> **起因**：核查"原项目是否有业务远程调用"时实测发现——老项目**全项目只有 5 处 `@FeignClient`**
> （`mall-auth` 2 处：`mall-admin` / `mall-portal`；`mall-demo` 3 处示例），
> **业务服务（admin / portal / search）之间零 RPC**，各自**直连同一个 `mall` 库**、跨域数据靠"直接查表"。
>
> **两个结论**：
> 1. 我们迁移期的「跨域只读」是**照抄老项目行为**，不是引入的差异（`pms_*` / `sms_*` / `oms_*` 直读为原样复刻）；
> 2. 真正待解决的不是"拆库"，而是 **数据所有权不清（每个服务都在读写别人的表）**。

### 8.1 核心原则（顺序不能反）

> **先解耦"访问方式"（改成 API / 事件），再分离"存储"（拆库）。**
> 顺序反了 → 代码里所有跨库 JOIN 与跨域直写立刻全废，迁移直接停摆。

### 8.2 当前表归属冲突清单（拆库前置，必须先理清）

| 表 | 拥有者（写方） | 冲突点 | 目标归属 |
|---|---|---|---|

### 8.3 四阶段路线（每阶段可独立验收）

| 阶段 | 时机 | 动作 | 验收标准 |
|---|---|---|---|
| **0** | 迁移期（当前） | 共库 + 跨域只读 + TODO 登记（**已完成，别动**） | 与老服务逐字节一致 |
| **1** | 老服务下线后 | **解耦"跨域写"**：`pms_sku_stock` / `sms_coupon_history` / `oms_order*` / `ums_member` → Feign（或 Outbox + 事件） | 门户代码里**再无跨域 INSERT/UPDATE**；并发下单/领券不丢不重 |
| **2** | 阶段 1 后 | **解耦"跨域读"**：`pms_*` / `sms_*` → Feign + 缓存（首页聚合尤其适合"Feign + 缓存 + 降级"） | 门户无跨域 SELECT；对方改表不需重跑门户 MBG |
| **3** | 阶段 2 后 | **物理拆库**：每服务独立 schema（先同实例不同库），各自连接串 | 跨库访问 = 0，拆库退化为"改配置" |
| 4（可选） | 长期 | Outbox + 幂等 + 定时对账 | 差异可告警、可回补 |

### 8.4 与本文其他章节的对应关系

- **#12 跨域直写 + 无对账** → 属**阶段 1**，是本文最该先做的一项；
- **#5 多表 JOIN 笛卡尔积**、**四、模拟真实业务验证 #6 对账演练** → 属**阶段 1/2**（对账是"拆库前必做"）；
- **五、两阶段边界（纪律）** → 与本节的阶段划分一致：**单库阶段只用本地事务，拆库后才谈分布式方案**；
