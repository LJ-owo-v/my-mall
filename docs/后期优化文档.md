# 后期优化文档

## 一、商品促销（calcCartPromotion）问题

按严重程度从高到低排列。

---

### 🔴 严重程度：高

#### 1. 库存超卖风险

**问题：**
```java
cartPromotionItem.setRealStock(skuStock.getStock() - skuStock.getLockStock());
```
只是展示用，没有加锁。高并发下多个用户同时看到有库存，都下单成功，导致超卖。

**优化方案：**
下单扣库存时用乐观锁：
```xml
UPDATE pms_sku_stock
SET stock = stock - #{quantity}, lock_stock = lock_stock + #{quantity}
WHERE id = #{id} AND stock >= #{quantity}
```
返回影响行数=0说明库存不足，回滚事务并提示"库存不足"。

**涉及文件：** 下单Service、PmsSkuStockMapper.xml

---

#### 2. 并发价格/库存变化

**问题：**
用户在购物车页看到的促销价，到下单时可能已经变了（运营改了促销价、别人买光了库存、促销过期了）。如果直接用购物车算好的价格下单，会导致价格不一致。

**优化方案：**
下单时必须重新查询促销信息和库存，重新计算价格，不能用购物车页传过来的价格。
- 重新查商品促销价
- 重新查库存
- 重新算满减/折扣
- 对比用户看到的价格，如果变化了提示用户"商品价格已变动，请确认"

**涉及文件：** 下单Service

---

### 🟡 严重程度：中

#### 3. 促销过期判断不严谨

**问题：**
`calcCartPromotion` 只根据 `promotionType` 计算优惠，没有判断促销是否在有效期内。促销过期后用户还能看到促销价。

**优化方案：**
查询促销信息时加时间条件：
```xml
WHERE p.id IN (...)
  AND (p.promotion_start_time IS NULL OR p.promotion_start_time <= NOW())
  AND (p.promotion_end_time IS NULL OR p.promotion_end_time >= NOW())
```
或者在 Service 层判断，过期的促销按无优惠处理。

**涉及文件：** PortalProductDao.xml、calcCartPromotion

---

#### 4. 满减分摊精度问题

**问题：**
满减按比例分摊到每件商品，用 `divide(totalAmount, RoundingMode.HALF_EVEN)` 可能出现分摊后合计不等于满减金额（四舍五入误差）。

**优化方案：**
最后一件商品用"满减总额 - 已分摊总额"，保证合计准确：
```java
BigDecimal allocated = BigDecimal.ZERO;
for (int i = 0; i < itemList.size(); i++) {
    if (i == itemList.size() - 1) {
        // 最后一件用减法，保证合计准确
        reduceAmount = fullReduction.getReducePrice().subtract(allocated);
    } else {
        reduceAmount = originalPrice.divide(totalAmount, RoundingMode.HALF_EVEN)
                .multiply(fullReduction.getReducePrice());
        allocated = allocated.add(reduceAmount);
    }
}
```

**涉及文件：** calcFullReductionPromotion

### 🟢 严重程度：低

#### 5. 多表JOIN笛卡尔积

**问题：**
`getPromotionProductList` 三个 LEFT JOIN（sku + ladder + full_reduction），一个商品10个SKU + 3个阶梯 + 2个满减 = 60行，MyBatis去重合并。

**优化方案：**
拆成多次单表查询，在Service层组装：
```java
// 1. 查商品基本信息
// 2. 批量查SKU
// 3. 批量查阶梯折扣
// 4. 批量查满减规则
// 5. Service层组装
```
购物车商品少的时候影响不大，商品多了再优化。

**涉及文件：** PortalProductDao.xml、PromotionServiceImpl

**问题：**
一个商品只能有一个 `promotionType`，单品促销、阶梯打折、满减不能同时生效。

**优化方案：**
如果业务需要叠加，改成多个促销字段或促销活动表，计算时按优先级叠加。现阶段业务设计如此，不需要改。

## 二、优惠券领取（add）问题

### 🔴 严重程度：高

#### 7. 高并发下优惠券超发

**问题：**
```java
if (coupon.getCount() <= 0) {
    Asserts.fail("优惠券已经领完了");
}
// ... 插入领取记录
coupon.setCount(coupon.getCount() - 1);
couponMapper.updateByPrimaryKey(coupon);
```
高并发下多个用户同时查到 count>0，都领成功，count变成负数，超发。

**优化方案：**
用乐观锁，更新时加条件：
```xml
UPDATE sms_coupon
SET count = count - 1, receive_count = receive_count + 1
WHERE id = #{id} AND count > 0
```
返回影响行数=0说明没抢到，回滚事务并提示"手慢了，优惠券已被抢完"。

**涉及文件：** SmsCouponMapper.xml、领券Service

## 三、交易域（门户下单 / 支付 / 超时取消）问题

> 对应改造批次：D10a 下单、D10b 支付与退货、D10c MQ 超时取消。

### 🔴 严重程度：高

#### 9. 锁库存丢失更新（超卖根因）　✅ **已完成（2026-10-15）**

> **修复结果**：JMeter 9 会员并发抢可售 5 件 —— 优化前**成功 9 单**（超卖 4 件、`lock_stock=2` 丢 7 次），优化后**成功 5 单**（零超卖、`lock_stock=5` == 明细 5）；A1/A2/A4/A5 断言由 FAIL 转为**全 PASS**。
> **改动**：`PortalOrderDao.lockStockSafely`（原子条件更新 + 影响行数判定）+ `lockStock()` 先合并同 SKU 数量再逐个加锁。
> **证据**：`mall-work\stress\result\evidence-before.txt` / `evidence-after.txt`；台账 `replace-log.md` 2026-10-15 行。

**问题：**
```java
// OmsPortalOrderServiceImpl.lockStock
PmsSkuStock skuStock = skuStockMapper.selectByPrimaryKey(cartPromotionItem.getProductSkuId());
skuStock.setLockStock(skuStock.getLockStock() + cartPromotionItem.getQuantity());
skuStockMapper.updateByPrimaryKeySelective(skuStock);
```
读整行 → 应用层加 → 整行回写，**无守卫**。并发两单都读到 `lock_stock=0`，各自写 `0+qty` → 后写覆盖先写，丢失一次锁定。
`hasStock()` 读的是另一条查询算出的 `realStock`，与 `lockStock` 是两条独立语句 → **TOCTOU**。
另外 `updateByPrimaryKeySelective` 会用 select 时刻的**旧快照**覆盖 `stock`/`sale` 等列。

**优化方案：**
原子自增 + 条件守卫，影响行数=0 即库存不足：
```xml
UPDATE pms_sku_stock
SET lock_stock = lock_stock + #{quantity}
WHERE id = #{skuId} AND stock - lock_stock >= #{quantity}
```
```java
if (affected == 0) {
    Asserts.fail("库存不足，无法下单");   // 文案与老服务一致，响应契约不变
}
```
要点：① 同一购物车里**同 sku 出现多次要合并累加**，否则逐条判断仍可能部分成功；② 失败必须靠 `@Transactional` 整体回滚；③ 检查与扣减合一后，`hasStock()` 只保留"提前提醒"作用，不再作为并发安全依据。

**涉及文件：** OmsPortalOrderServiceImpl.lockStock、新增 PortalOrderDao.lockStockSafely + PortalOrderDao.xml

#### 10. 超时未支付订单**永远不会取消**

**问题：**
`generateOrder` 末尾发延迟消息，但 `sendDelayMessageCancelOrder()` 与写单不在同一原子语义里：
- 先发消息后提交 → 消息先到，`cancelOrder` 查不到订单 → 白取消；
- 先提交后发消息（现状）→ **提交成功但发送失败（进程被 kill / broker 抖动）→ 消息丢失，订单永远停在待付款**，锁定的库存与券也永不释放。
兜底的 `OrderTimeOutCancelTask` 在原项目里 `@Component` **被注释掉**、`@Scheduled` 方法还是 `private` → **实际不生效**，等于零兜底。

**优化方案：**
① 消息发送挪到**事务提交之后**：`TransactionSynchronizationManager.registerSynchronization(...afterCommit...)`；
② 真正的兜底用**本地消息表（Outbox）**：与订单同库同事务写一条待投递记录 → 定时任务扫描投递 + 重试；
③ 消费端幂等：`cancelOrder` 内部用 `UPDATE oms_order SET status=4 WHERE id=? AND status=0`，影响行数=0 直接返回；
④ 定时任务**主动补偿**：扫 `status=0 AND create_time < NOW()-15min` 的订单直接取消（不依赖 MQ）。

**涉及文件：** OmsPortalOrderServiceImpl、CancelOrderSender/Receiver、OrderTimeOutCancelTask、新增 mq_outbox 表

---

#### 11. 延迟队列队头阻塞（TTL 方案固有缺陷）

**问题：**
`CancelOrderSender` 用**消息级 TTL**（`setExpiration`）投到同一个 TTL 队列。RabbitMQ 只在**队头**判断过期：队首消息 TTL 15 分钟未到期时，它后面那条 TTL 1 秒的消息**也不会被投递**，要等队首过期才一起走。订单取消的准点性随队列深度劣化。

**优化方案：**
① 装 `rabbitmq_delayed_message_exchange` 插件，改用 `x-delayed-message` 交换机（按消息延迟时间精确投递，无队头阻塞）；
② 或"时间轮 / 分级延迟队列"：把延迟档位拆成多个队列（1min/5min/15min），各自 TTL 固定；
③ 与第 10 条用同一个定时补偿任务兜底（成本最低，可与插件方案并行）。

**涉及文件：** RabbitMqConfig、CancelOrderSender、QueueEnum

#### 12. 跨域直写 + 无对账（最终一致性缺口）

**问题：**
一个本地事务里直写了 5 张**不属于门户**的表：`oms_order`/`oms_order_item`（订单域）、`pms_sku_stock`（商品域）、`sms_coupon_history`（营销域）、`ums_member.integration`（会员域）。
迁移期同库可行，但域边界已破；一旦拆库，本地事务立刻失效，且现在**没有任何对账/补偿机制**，中间态无人发现。

**优化方案：**
① 跨域写改 Feign 调用对应服务（`my-mall-product`/`my-mall-marketing`/`my-mall-user`）或发领域事件；
② 拆库时上 **Outbox + 幂等 + 定时对账**（对比订单实付与各域扣减记录，发现差异自动告警/回补）；
③ 现阶段先登记 TODO，**不改契约**（响应字节必须与老服务一致）。

**涉及文件：** OmsPortalOrderServiceImpl、PortalOrderDao.xml、docs/ai/64-portal.md 的 TODO 区

#### 14. 下单幂等（重复提交出两单）

**问题：**
现在靠"下单时删除购物车行"隐式防重：用户连点两次或网络重试，若第一次事务还没提交，第二次仍能读到购物车 → 生成两张订单（并各锁一次库存）。

**✅ 已完成（2026-10-15）—— 实采「方案③：cartIds 作幂等键」**

> **修复结果**：JMeter 2 线程并发提交**完全相同**的下单请求 —— 优化前生成 **2 张订单**（同一秒创建、各锁一次库存），优化后**仅 1 张**；I1/I3/I4 断言由 FAIL 转 **全 PASS**。
> **改动**：`PortalOrderDao.occupyCartItems`（原子抢占购物车行）+ `generateOrder` 事务开头判定 `affected < cartIds.size()`。
> **证据**：`mall-work\stress\result\evidence-idem-{before,after}.txt`；台账 `replace-log.md` 2026-10-15 行。

**为什么没采用下面两条方案（① / ②）**：

| | ① 前端令牌 + Redis SETNX | ② 唯一索引兜底 | **③ cartIds 抢占（实采）** |
|---|---|---|---|
| 改接口 | ❌ 要加 `token` 字段 | ✅ 不用 | ✅ **不用** |
| 改前端 | ❌ 要配合 | ✅ 不用 | ✅ **不用** |
| 改表结构 | ✅ 不用 | ❌ 要加索引 | ✅ **不用** |
| 顺带修问题 | ❌ | ❌ | ✅ **修掉"下单后购物车未清空"** |

**③ 的关键洞察**：`cartIds` **本身就是一个"一次性"资源** —— 购物车行被消费后即应失效，因此**无需再引入额外的幂等键**。把「删购物车」从**事后（原第 13 步）**提前为**事前原子抢占**：

```xml
<update id="occupyCartItems">
    UPDATE oms_cart_item
    SET delete_status = 1, modify_date = NOW()
    WHERE member_id = #{memberId}
      AND delete_status = 0          <!-- ★ 条件守卫：并发下只有一个请求能置 1 -->
      AND id IN (...)
</update>
```
```java
// generateOrder 事务开头（读购物车之后、锁库存之前）
int occupied = portalOrderDao.occupyCartItems(currentMember.getId(), cartIds);
if (occupied < cartIds.size()) {
    Asserts.fail("订单正在处理中，请勿重复提交");
}
```

**事务边界说明**：抢不到的请求 `affected=0`（**未改到任何行**），其回滚**不会影响已提交方**、也不会误删购物车。

**遗留可选增强**：若将来需要防"跨购物车"的重复下单（如同一会员用不同购物车行连续下单），再引入 ① 的前端令牌；当前场景下 ③ 已覆盖"连点两次 / 网络重试 / Feign 重放"。

**原优化方案（供参考）：**
① 前端带幂等令牌（`token`），后端 Redis `SETNX` 占位，重复请求直接返回原订单；
② 或 DB 兜底：订单号唯一索引 + `(member_id, 幂等键)` 唯一索引，冲突时查回已有订单。

**涉及文件：** OmsPortalOrderController.generateOrder、OmsPortalOrderServiceImpl

#### 15. 取消/退款失败无重试，库存与券不回退

**✅ #15-A 已完成（2026-10-15）—— 同一订单被取消两次 → 库存/券/积分重复退还**

> **修复结果**：验证 5 项全 PASS（下界保护 SQL 层必现对照、正常取消、重复取消 ×3、定时任务批量 3 张、全库负锁定 = 0）；日志实证 `Updates:1` 全链路正确、无异常无回滚。
> **改动**：`PortalOrderDao.releaseSkuStockLockSafely`（下界保护）+ `updateOrderStatusByIdIfPending`（原子裁决）+ `cancelOrder`/`cancelTimeOutOrder` 改为先裁决后释放。
> **证据**：`mall-work\stress\result\evidence-cancel-after.txt`；台账 `replace-log.md` 2026-10-15 行。

**实际缺陷（3 处，代码审计得出）**：

| # | 缺陷 | 后果 |
|---|---|---|
| ① | `releaseSkuStockLock` **无下界保护**（`SET lock_stock = lock_stock - ?` 无 `AND lock_stock >= ?`） | 任何一次重复调用都把 `lock_stock` 减成**负数** → 库存虚高（**库中曾实存 −24/−8/−8**） |
| ② | `cancelOrder` **先查后写**（`SELECT` 带 `status=0` → 判断 → `UPDATE` 无 `status` 条件） | 并发下两个请求都能通过检查 → **各释放一次** |
| ③ | `cancelTimeOutOrder` **批量 `UPDATE` 无 `status` 条件** | 无法定位"我真正关掉了哪些" → 可能重复释放 |

**修复做法（用"条件更新的影响行数"裁决谁有权释放资源）**：

```xml
<!-- ① 下界保护 -->
<update id="releaseSkuStockLockSafely">
    UPDATE pms_sku_stock SET lock_stock = lock_stock - #{quantity}
    WHERE id = #{skuId} AND lock_stock >= #{quantity}
</update>

<!-- ② 原子裁决 -->
<update id="updateOrderStatusByIdIfPending">
    UPDATE oms_order SET status = #{status} WHERE id = #{orderId} AND status = 0
</update>
```
```java
// cancelOrder / cancelTimeOutOrder 统一改为：
int closed = portalOrderDao.updateOrderStatusByIdIfPending(orderId, 4);
if (closed == 0) return / continue;        // 已被其他路径处理 → 绝不重复释放
for (OmsOrderItem item : itemList) {       // 逐 SKU + 下界保护
    portalOrderDao.releaseSkuStockLockSafely(item.getProductSkuId(), item.getProductQuantity());
}
```

**两个重要澄清**（修正本章节原先的描述）：

| 原先描述 | 实际情况 |
|---|---|
| "任一步异常，前面已成功的步骤**不回滚**（非同一事务或异常被吞）" | ⚠️ **代码中没有 try-catch 吞异常**，且 `@Transactional` **存在** → `RuntimeException` 会**整体回滚**。真正的可靠性问题是 **`rollbackFor` 用 Spring 默认值**（受检异常不回滚）+ **无重试机制**，属 **#15-B** 范围 |
| "定时任务重跑 → 重复释放" | ⚠️ **不成立**：`getTimeOutOrders` 带 `WHERE o.status = 0`，**已关闭的订单捞不到**。真实风险仅剩「MQ 与定时任务**同毫秒撞车**」这一窄路径。但一旦命中即**永久污染库存**，故仍按"**靠不变量而非概率**"加固 |

**仍待做（#15-B 可靠性部分）**：
① 两个取消方法显式加 `@Transactional(rollbackFor = Exception.class)`（当前受检异常不回滚）；
② 释放动作失败的重试机制（或"状态机 + 补偿"：先置取消中 → 逐个释放（各自幂等）→ 全成功才置已取消，失败留给定时任务重试）。
> 原 B 中的"批处理事务粒度过粗"已随本次改造（**逐单原子裁决 → 天然成为单订单语义**）**顺带解决**。

**原优化方案（供参考）：**
① 全部收敛到同一个 `@Transactional` 内（当前库同库可做到）；
② 更稳的做法是拆成"状态机 + 补偿"：先置取消中 → 逐个执行释放动作（各自幂等）→ 全部成功才置已取消，失败的留给定时任务重试。

**涉及文件：** OmsPortalOrderServiceImpl.cancelOrder/cancelTimeOutOrder、PortalOrderDao.xml

#### 16. 支付回调未校验金额、无回调幂等

**问题：**
`AlipayServiceImpl.notify` 验签后只看 `trade_status == TRADE_SUCCESS` 就 `paySuccessByOrderSn(out_trade_no, 1)`：
- **不比对回调金额与订单金额**（理论可被"小额支付大额订单"绕过）；
- 支付宝会**重复投递**同一回调，重复执行 `paySuccess`（虽然有 `status` 判断，但缺少显式幂等与日志留痕）；
- `query()` 在异常分支下 `response` 为 null 会 **NPE**（原项目缺陷，照抄保留）。

**优化方案：**
① 回调里比对 `total_amount` 与 `oms_order.pay_amount`，不一致直接 `failure` 并告警；
② `paySuccess` 用条件更新做幂等：`UPDATE oms_order SET status=1, payment_time=NOW() WHERE id=? AND status=0`；
③ 记录回调原文（含 `trade_no`）便于对账；④ `query()` 补判空。

**涉及文件：** AlipayServiceImpl、OmsPortalOrderServiceImpl.paySuccess

#### 17. 前台取消订单接口冗余且实现错误

**问题：**
原项目 portal（前台）存在两个取消订单接口，实现不一致：

| 接口 | summary | 调用方法 | 实际效果 |
|---|---|---|---|
| `POST /cancelOrder` | 取消单个超时订单 | `sendDelayMessageCancelOrder(orderId)` | 发延迟消息，60分钟后才取消 ❌ |
| `POST /cancelUserOrder` | 用户取消订单 | `cancelOrder(orderId)` | 立即取消 ✅ |

具体问题：
1. **`/cancelOrder` 实现错误**：用户/管理员点取消却调用 `sendDelayMessageCancelOrder`，读取 `normalOrderOvertime`（如60分钟）作为延迟时间，导致点了取消后要等60分钟才真正释放库存、券、积分，期间库存仍被锁定；
2. **前台语义不合理**：`/cancelOrder` 的 summary 是"取消单个超时订单"，这是后台管理员视角，前台用户不会有"取消超时订单"这种操作；
3. **接口冗余**：两个接口底层都应该是"立即取消订单"，`/cancelOrder` 属于历史遗留（早期实现写错，后来加了 `/cancelUserOrder` 修正，但旧接口没删）。

**优化方案：**
① 前台**只实现 `/cancelUserOrder`** 作为用户取消订单接口，直接调用 `cancelOrder(orderId)` 立即取消，**不实现 `/cancelOrder`**（原项目的错误冗余接口不需要1:1照抄）；
② 若保留 `/cancelOrder`，必须改为也调用 `cancelOrder(orderId)` 立即取消，不能再发延迟消息；
③ 取消逻辑必须幂等：`UPDATE oms_order SET status=4 WHERE id=? AND status=0`，影响行数=0直接返回（已取消/已支付的订单不能重复取消）；
④ 真正的"超时自动取消"由 MQ 延迟队列 + 定时任务兜底完成，不需要暴露前台接口手动触发。

**涉及文件：** OmsPortalOrderController（只保留 cancelUserOrder）、OmsPortalOrderServiceImpl.cancelOrder/sendDelayMessageCancelOrder

#### 18. 订单号依赖 Redis，回滚浪费号段

#### 19. 热点库存行锁竞争

**问题：**
`pms_sku_stock` 单行在秒杀场景被高频 `UPDATE`，行锁排队；再加上同一事务里还写 `oms_order`/`oms_order_item`/券/积分，持锁时间被拉长。

**优化方案：**

② 秒杀场景用"库存分段/预扣减 + 异步落单"（会改变响应语义，**与老服务对齐期间不做**）；
③ 读写分离或热点行拆分。

**涉及文件：** OmsPortalOrderServiceImpl.generateOrder 事务范围

#### 20. 加购不补全价格 → 下单 NPE 500（2026-10-13 联调实测）

**问题：**
`/cart/add` 直接落库前端传入的 `OmsCartItem`，**不按 skuId 回查 SKU 补全** `price`/`productName`/`productPic`：
```java
cartItem.setMemberId(...); cartItem.setMemberNickname(...); cartItem.setDeleteStatus(0);
OmsCartItem existCartItem = getCartItem(cartItem);
if (existCartItem == null) { cartItem.setCreateDate(new Date()); count = cartItemMapper.insert(cartItem); } ...
```
只要调用方（新前端、第三方、脚本）**只传 `productSkuId` + `quantity` 而漏传 `price`**：
购物车行 `price = NULL` → `generateConfirmOrder` / `generateOrder` 里的 `calcCartAmount`：
```java
totalAmount = totalAmount.add(item.getPrice().multiply(new BigDecimal(item.getQuantity())));
```
**NPE → HTTP 500**，前端拿不到可读原因。

**实测证据（2026-10-13）**：漏传 price 加购 → `oms_cart_item.price = NULL` → `POST /order/generateConfirmOrder`、`POST /order/generateOrder` **均 500**；补传 price（=sku 真实价 5599.00）→ 两者均 **200**，下单成功（`orderSn=202610130101000001`、明细 1 条、`lock_stock` 0→1）。

**与老项目的关系**：已逐行比对老项目 `OmsCartItemServiceImpl.add(...)` —— **同样不查 SKU 补价**，属**既有健壮性缺陷**（迁移期按"行为一致"原则保留未修）。

**优化方案：**
① 后端在 `add` 内按 `productSkuId` 回查 `pms_sku_stock` + `pms_product`，**强制覆盖** `price`/`productName`/`productPic`/`productSkuCode`（防前端漏传或传错价）；
② 至少在 `calcCartAmount` 前做**空值校验**并返回可读业务错误（如"购物车价格缺失，请重新加购"），不要裸 NPE；
③ 更彻底：`oms_cart_item.price` 加 `NOT NULL` 约束 + 加购入口校验。

**涉及文件：** OmsCartItemServiceImpl.add、OmsPortalOrderServiceImpl.calcCartAmount、`oms_cart_item` 表约束

## 四、模拟真实业务验证（优化的**前置**，不能跳过）

> 原则：**先证明问题真实存在，再动手优化**；每项优化都要有"优化前 vs 优化后"的实测对比。

### 1. 并发下单压测（证明超卖）
- 造数：1 个 sku，`lock_stock=0`、`stock=N`（如 10）；准备 M 个购物车行（同 sku 多行 + 多 sku 组合）
- 压测：并发 `N+3` 个下单请求**打同一个 8092 实例**
- 断言：成功单数 ≤ N；`stock - lock_stock >= 0`；`SUM(oms_order_item.product_quantity) <= N`
- 记录基线：成功单数 / `lock_stock` 终值 / 是否出现负余量 → 作为优化后的对照

### 2. 超时取消链路压测（证明队头阻塞）
- 批量下单不付款（TTL 全为 15 分钟）→ 观察延迟队列深度与消息投递时间
- 追加一条极短 TTL 消息，验证是否被队首阻塞
- 断言：订单在 15 分钟 + 容差内自动取消，且 `lock_stock` 被释放

### 3. MQ 丢消息演练（证明"永不取消"）
- 下单成功后立刻 `kill 8092` 或断开 RabbitMQ → 重启后观察该订单是否被取消
- 断言：现状下**不会**被取消（复现问题）→ 做 Outbox/定时补偿后**会被取消**（验证修复）

### 4. 重复提交演练（证明幂等缺口）
- 同一购物车在 500ms 内并发提交 2 次
- 断言：现状可能生成 2 单 → 加幂等键后只生成 1 单

### 5. 数据量与脏数据准备
- `oms_order` 当前仅 77 行，压不出性能问题：先造量（如 1 万单）再看列表/详情分页
- 必须校准脏数据：`pms_sku_stock` 存在负 `lock_stock`（sku 98 = −24、102 = −8）
- 造数统一打标记（如 `note='D10A-TEST'`），便于精准清理，避免污染逐字节验收

### 6. 对账演练（拆库前必做）
- 手工制造中间态（如把 `pms_sku_stock.lock_stock` 改掉一行）
- 跑对账脚本，断言能发现"订单已付但库存未扣/券未核销"的差异

## 七、通用优化方向

### 1. 分布式锁
秒杀、领券、扣库存等并发场景，用 Redis 分布式锁（Redisson）。
> 注意：能靠 **DB 条件更新（乐观锁）** 解决的（如 #9 锁库存、#7 领券），优先用 DB，不要引入分布式锁——锁会带来超时、续期、死锁与性能开销。

### 2. 异步处理
- 下单成功后发MQ，异步扣库存、减优惠券、加积分
- 订单超时取消用延迟队列
> 注意：**异步化会改变响应语义**（"下单成功"→"受理中"），与老服务逐字节对齐期间禁止；且必须先解决 #10（消息与 DB 的原子性/Outbox）。

### 3. 缓存
- 商品促销信息缓存到 Redis，减少数据库查询
- 优惠券信息缓存，领券时更新缓存
> 注意：库存类数据**不要缓存**（实时性要求高，会放大超卖）。

### 4. 限流
- 秒杀接口限流，防止恶意刷接口
- 领券接口按用户限流

### 5. 最终一致性（交易域新增）
- **本地消息表（Outbox）** 替代"直接发 MQ"：同库同事务写待投递记录 → 定时投递 + 重试 + 去重
- 消费端**幂等**：状态机条件更新（`WHERE status=0`）+ 唯一索引兜底
- **定时对账**：订单实付 vs 各域扣减记录，发现差异告警并回补

### 6. 事务边界（交易域新增）
- **缩短事务**：只包 DB 写；远程调用（Feign）、MQ 发送、缓存操作移到事务外
- MQ 发送放 `afterCommit`（`TransactionSynchronizationManager`），避免"消息先到数据后到"
- 单库阶段用本地 `@Transactional` 即可；**拆库后才考虑** Seata/Outbox 等分布式方案

### 7. 压测与观测（交易域新增）
- 用 JMeter/wrk 做并发下单、领券压测，**先证明问题存在**再优化
- 关键链路加指标：下单成功率、库存负余量次数、消息投递延迟、取消订单数
- 每项优化都要留"优化前 / 优化后"实测对比，可回滚

## 八、架构演进：数据所有权与拆库路线（2026-10-11 新增）

> **起因**：核查"原项目是否有业务远程调用"时实测发现——老项目**全项目只有 5 处 `@FeignClient`**
> （`mall-auth` 2 处：`mall-admin` / `mall-portal`；`mall-demo` 3 处示例），
> **业务服务（admin / portal / search）之间零 RPC**，各自**直连同一个 `mall` 库**、跨域数据靠"直接查表"。
>
> **两个结论**：
> 1. 我们迁移期的「跨域只读」是**照抄老项目行为**，不是引入的差异（`pms_*` / `sms_*` / `oms_*` 直读为原样复刻）；
> 2. 真正待解决的不是"拆库"，而是 **数据所有权不清（每个服务都在读写别人的表）**。

### 8.1 核心原则（顺序不能反）

> **先解耦"访问方式"（改成 API / 事件），再分离"存储"（拆库）。**
> 顺序反了 → 代码里所有跨库 JOIN 与跨域直写立刻全废，迁移直接停摆。

### 8.2 当前表归属冲突清单（拆库前置，必须先理清）

| 表 | 拥有者（写方） | 冲突点 | 目标归属 |
|---|---|---|---|
| `oms_order` / `oms_order_item` | my-mall-order | portal 跨域**读**（下单/详情/取消） | 归 order，portal 改 Feign |
| `pms_sku_stock` | my-mall-product | portal 跨域**直写**（下单锁库存 / 取消释放） | 归 product，portal 改 Feign（**并发正确性关键**） |
| `sms_coupon_history` | my-mall-marketing | portal 跨域**直写**（领券） | 归 marketing，portal 改 Feign |
| `ums_member_level` | portal（自有：会员等级折扣） | **my-mall-user 也有 `UmsMemberLevelController`** → 归属未定 | **待拍板**（见 8.5） |
| `cms_subject` | **无归属服务** | 门户首页专题要用 | **待拍板**（见 8.5） |
| 其余 `pms_*` / `sms_*`（约 17 张） | product / marketing | portal 跨域**只读**（耦合表结构：对方改表需重跑门户 MBG） | 保持只读至阶段 2 |

### 8.3 四阶段路线（每阶段可独立验收）

| 阶段 | 时机 | 动作 | 验收标准 |
|---|---|---|---|
| **0** | 迁移期（当前） | 共库 + 跨域只读 + TODO 登记（**已完成，别动**） | 与老服务逐字节一致 |
| **1** | 老服务下线后 | **解耦"跨域写"**：`pms_sku_stock` / `sms_coupon_history` / `oms_order*` / `ums_member` → Feign（或 Outbox + 事件） | 门户代码里**再无跨域 INSERT/UPDATE**；并发下单/领券不丢不重 |
| **2** | 阶段 1 后 | **解耦"跨域读"**：`pms_*` / `sms_*` → Feign + 缓存（首页聚合尤其适合"Feign + 缓存 + 降级"） | 门户无跨域 SELECT；对方改表不需重跑门户 MBG |
| **3** | 阶段 2 后 | **物理拆库**：每服务独立 schema（先同实例不同库），各自连接串 | 跨库访问 = 0，拆库退化为"改配置" |
| 4（可选） | 长期 | Outbox + 幂等 + 定时对账 | 差异可告警、可回补 |

### 8.4 与本文其他章节的对应关系

- **#12 跨域直写 + 无对账** → 属**阶段 1**，是本文最该先做的一项；
- **#5 多表 JOIN 笛卡尔积**、**四、模拟真实业务验证 #6 对账演练** → 属**阶段 1/2**（对账是"拆库前必做"）；
- **五、两阶段边界（纪律）** → 与本节的阶段划分一致：**单库阶段只用本地事务，拆库后才谈分布式方案**；
- **#9 锁库存丢失更新（超卖）** → 即便阶段 1 改成 Feign，`pms_sku_stock` 的并发扣减仍需条件更新/原子扣减兜底。

### 8.5 必须先拍板的两处归属（否则阶段 3 卡住）

| 表 | 选项 | 建议 |
|---|---|---|
| `ums_member_level` | ① 归 portal（会员侧）② 归 user（管理侧） | 归 **user**（等级定义属用户域），portal 改 Feign 读；无论选哪个，**必须只有一个写方** |
| `cms_subject` | ① 新建 content 服务 ② 归 product ③ 归 portal | 当前仅门户使用 → **暂归 portal 自有**（从"跨域表"降为"自有表"），将来有内容管理需求再拆 content 服务 |

### 8.6 下线硬前置（与拆库无关，但不做就下不了线）

| # | 项 | 说明 |
|---|---|---|
| 1 | **auth 的 2 处 Feign 改指向** | `@FeignClient("mall-admin")` → `my-mall-user`；`@FeignClient("mall-portal")` → `my-mall-portal`。**路径无需改**（新服务保留了 `/admin`、`/sso` 前缀）→ 否则老服务一下线，**管理员+会员登录全挂** |
