【实测发现的三个问题（本阶段修复其中 2 个）】

问题 1（已修复）：无明细的订单永远不会被兜底取消
  根因：getTimeOutOrders 的 SQL 带 AND EXISTS (SELECT 1 FROM oms_order_item ...)
        → 要求订单【必须有明细】才会被扫描到 → 无明细订单被永久排除

  实测现场（真实数据）：
    订单 73：status=0（待付款）、明细数=0、创建于 2023-05-11
             已超时 1253 天（约 3.4 年）仍未被取消
    带 EXISTS 时查询 → 0 条（查不到它）
    去掉 EXISTS 后   → 1 条（能查到）

  安全性验证（逐项核对，确认无明细时安全）：
    · 关单        updateOrderStatusByIdIfPending(id, 4)          → 正常改状态
    · 5.1 释放库存 if (!CollectionUtils.isEmpty(itemList))        → 判空保护，跳过
    · 5.2 退券     updateCouponStatus(...) 内部 if (couponId==null) return → 跳过
    · 5.3 退积分   if (getUseIntegration() != null)              → 判空，跳过
    订单 73 实测：coupon_id=NULL、use_integration=NULL、明细=0
    → 三个释放动作全部自然跳过，【仅关单】✅

问题 2（已修复）：延迟队列队头阻塞（TTL 方案固有，#11）
  根因：CancelOrderSender 用【消息级 TTL】，RabbitMQ 只在【队头】判断过期
        → 队首长 TTL 消息会把后面的短 TTL 消息堵住
  配置上已具备触发条件：normal_order_overtime=120 分钟、flash_order_overtime=60 分钟
  （两者不同 → 若同时存在两类订单，秒杀订单的取消会被普通订单堵住）
  RabbitMQ 实测：mall.order.cancel.ttl 队列有 1 条 ready 消息、consumers=0

问题 3（本次不修，用户决定）：
  消息在事务内发送 → 有"白取消"窗口；但有兜底纠正，影响不大

【修复】

① PortalOrderDao.xml 的 getTimeOutOrders：
     去掉 AND EXISTS (SELECT 1 FROM oms_order_item t2 WHERE t2.order_id = o.id)
     → 无明细订单也能被兜底扫描到（无明细时自然不释放任何资源，仅关单）

② OrderTimeOutCancelTask 的 cron：
     "0 0/10 * ? * ?"（10 分钟）→ "0 0/2 * ? * ?"（2 分钟）
     → 用更勤的扫描补偿队头阻塞导致的取消延迟
     （彻底解决需装 rabbitmq_delayed_message_exchange 插件，属运维侧改动，暂不做）
